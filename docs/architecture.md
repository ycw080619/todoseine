# 架构说明

## 一句话

把「导出文件」变成「待办清单」的一条单向管线，每一段都可替换。

## 分层

```
┌──────────────────────────────────────────────────────────┐
│  adapters/         导出文件 → Message                     │
│  ├── qq_txt        QQ 导出 txt                            │
│  ├── chatlab_json  ChatLab Format JSON / JSONL            │
│  └── <你的适配器>  实现 SourceAdapter.read()                │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  core/dedupe       去重（时间戳+发送者+长度+内容哈希）        │
│  core/classify     粗分类（闲聊 / 信息 / 风险）              │
│  core/extract      待办抽取（可解释规则）                    │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  core/store        SQLite（messages / todos）              │
│  core/sink_markdown Markdown（Obsidian 可直接用）            │
└──────────────────────────────────────────────────────────┘
```

## 为什么是「单向管线」而不是「实时监控」

实时监控需要读取客户端的加密数据库或窗口无障碍树，这两条路都会把项目拖进：
账号风险、版本维护、法律争议。而「导出的文件」是用户自己的数据，
处理它没有歧义。

代价是**非实时**：你导出一次，才处理一次。
这个取舍写在 README 第一行，不藏着。

## 为什么核心零依赖

- 装得上：`pip install` 不拉任何包，网络差的环境也能用
- 审得动：全部标准库，安全审计成本低
- 活得久：不受第三方库 break change 影响
- 可嵌入：别处 `import chat2todo` 不会被依赖树污染

可选依赖单独放 extras：`[api]` 才装 FastAPI。

## 去重设计

`(timestamp, sender_id, content_len, content_hash)`

- 前三项与 ChatLab 一致，保证两边增量导入互不重复
- 第四项解决「同一秒、同一人、等长但内容不同」的碰撞
- SQLite 层用 `UNIQUE` 约束兜底，重复导入恒等幂等

## 待办判定的可解释性

每条待办都存 `reason`（命中哪些词）与 `confidence`（0–1）。

这是刻意设计：规则引擎一定有误判，用户需要知道**为什么**系统认为这是待办，
才能决定信不信。这也为日后接入 LLM 留了对照基线——
LLM 版必须能说明「比规则好在哪」。

## 扩展点

| 想加什么 | 改哪里 |
|---|---|
| 新平台 | `adapters/` 加一个类并注册 |
| 新判定规则 | `core/extract.py` 的词表与权重 |
| 新输出格式 | `core/` 加一个 sink |
| 本地查询 | `api/`（可选依赖） |
| 定时处理 | 外部 cron 调用 `c2t import` 即可，不需要内置调度 |
