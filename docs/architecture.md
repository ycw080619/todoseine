# 架构说明

## 一句话

把「聊天记录」变成「待办清单」的一条单向管线，每一段都可替换；
实时监听只是给这条管线加了一个增量入口，不改变数据流向。

## 分层

```
┌──────────────────────────────────────────────────────────┐
│  输入通道                                                   │
│  ├── adapters/     导出文件 → Message（离线全量）            │
│  └── sources/uia   截图 + Win11 OCR → Message（在线增量）    │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  core/dedupe       去重（时间戳+发送者+长度+内容哈希）        │
│  core/classify     粗分类（闲聊 / 信息 / 风险）              │
│  core/extract      待办抽取（可解释规则）                    │
│  core/events       跨群同一件事归并                         │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  core/store        SQLite（messages / todos / trash …）    │
│  core/sink_markdown Markdown（Obsidian 可直接用）            │
│  qt/               看板、托盘、热键、截图建待办（PySide6）    │
└───────────────────────────┬──────────────────────────────┘
                            ▼
┌──────────────────────────────────────────────────────────┐
│  可选增强（默认按需开启，不接入也不影响主管线）               │
│  ├── core/privacy      全链路脱敏 + 日志过滤 + AI 明文开关    │
│  ├── core/archive      消息 Markdown 归档 + manifest 去重     │
│  ├── core/backup       每日 DPAPI 加密备份 / 回收站清理       │
│  ├── core/obsidian     双向同步（MD5 增量、冲突留档）          │
│  ├── core/desktop_link 脱敏 JSON/ICS + 本机回写接口           │
│  ├── core/hermes       本机 token 鉴权 / 巡检 / 每日汇总       │
│  ├── core/plugins      子进程隔离 + 安全模式 + 快照回滚        │
│  └── core/migrate      影子副本迁移（失败不碰正式库）          │
└──────────────────────────────────────────────────────────┘
```

## 可选增强模块的边界

这些模块都不进主数据流：关掉后主管线（导入 → 去重 → 抽取 → 入库 → 看板）
行为完全不变。它们共同遵守两条硬约束——

- **只碰自己的目录**：归档、备份、联动输出、汇总都写在库文件同目录下的子目录，
  不往用户的其他目录乱放；
- **只监听回环**：`desktop_link` / `hermes` 的 HTTP 服务只绑 `127.0.0.1`，
  随机端口 + token + Host/Origin 校验，外部机器连不上。

脱敏是唯一的横向切面：`core/privacy` 被归档、看板、日志、AI 四条路径共同调用，
白名单群只豁免「归档与看板展示」，云端 AI 请求默认一律强制脱敏；用户显式打开
「AI 明文」开关（需二次确认，可再按群号收窄）后才放行原文。

## 为什么是「只读通道」

实时监控原本是禁区：读客户端的加密数据库、往进程里注入钩子，都会把项目拖进
账号风险、版本维护、法律争议。

Qt 版走的是第三条路——**只截自己的屏幕认字**：

- 不注入、不 hook、不读 QQ 的任何存储文件，DDL / 内存 / 网络一概不碰；
- 用 Win11 自带的 `Windows.Media.Ocr`，离线可用；
- 截图前把进程设为 PerMonitorV2，避免 150% 缩放下截错区域。

代价是识别质量不如结构化接口：读不出群名与发送人（统一记成「OCR识别」），
同一句话重复滚动出现时靠三元组去重（内容 + 长度 + 时间窗）压住。
所以 OCR 只是「在线增量」，权威数据仍然是导出文件那条离线通道。

## 为什么核心零依赖

- 装得上：`pip install` 不拉任何包，网络差的环境也能用
- 审得动：全部标准库，安全审计成本低
- 活得久：不受第三方库 break change 影响
- 可嵌入：别处 `import todoseine` 不会被依赖树污染

PySide6 只在 `todoseine.qt` 这一层出现，`core/` 与 `adapters/` 不知道它存在。

可选依赖单独放 extras：`[api]` 才装 FastAPI。

## 去重设计

`(timestamp, sender_id, content_len, content_hash)`

- 前三项与 ChatLab 一致，保证两边增量导入互不重复
- 第四项解决「同一秒、同一人、等长但内容不同」的碰撞
- SQLite 层用 `UNIQUE` 约束兜底，重复导入恒等幂等

## 待办判定的可解释性

每条待办都存 `reason`（命中哪些词）与 `confidence`（0–1）。

这是刻意设计：规则引擎一定有误判，用户需要知道**为什么**系统认为这是待办，
才能决定信不信。这也为日后接入 LLM 留了对照基线——
LLM 版必须能说明「比规则好在哪」。

## 扩展点

| 想加什么 | 改哪里 |
|---|---|
| 新平台 | `adapters/` 加一个类并注册 |
| 新判定规则 | `core/extract.py` 的词表与权重 |
| 新输出格式 | `core/` 加一个 sink |
| 本地查询 | `api/`（可选依赖） |
| 定时处理 | 外部 cron 调用 `c2t import` 即可，不需要内置调度 |
